# RAG 功能全面评价

> 日期: 2026-05-31
> 目的: 对现有功能和实现技术进行全面客观评估，识别优势与不足

---

## 一、总评

项目在约两周内从基础的向量搜索演进为一套完整的企业级 RAG 系统，覆盖了文档入库、多路召回、上下文扩展、精排、两级检索、上下文管理、幻觉抑制七个领域。核心链路（RRF → SW → 两级检索 → Reranker → LLM）完整可用，在 20 万字长文档上验证通过。

**总体评分: 7.5/10** — 功能完整度 8 分，工程健壮性 7 分，性能优化 6 分，可观测性 8 分。

---

## 二、逐项评价

### 2.1 文档入库管线

| 维度 | 评价 | 评分 |
|:--|:--|:--|
| 格式支持 | PDF/TXT/DOCX 三种格式，覆盖常见需求 | 7/10 |
| 解析质量 | PyMuPDF 文本提取正常；OCR 兜底但仅检测首页 CJK，封面图会误判 | 6/10 |
| 切片策略 | 4 种策略覆盖主要场景，recursive 三段降级设计优秀 | 8/10 |
| 去重机制 | MD5 哈希去重，简单有效 | 7/10 |
| AI 摘要 | 上传时自动生成 5-8 句中文摘要，LLM 调用 | 8/10 |

**优势**: 切片策略设计完善，recursive 三段降级（段落→句子→滑动窗口）确保任何格式的文本都能被合理切分。AI 摘要一次生成多处复用（前端预览 + 两级检索）。

**不足**: 
- OCR 检测逻辑简陋（只检查首页），实际生产环境中扫描版 PDF 占比不低
- 不支持 `.md` 之外的结构化文档（如 `.csv`、`.html`）
- 缺少文档更新/版本管理机制

---

### 2.2 向量存储与 Embedding

| 维度 | 评价 | 评分 |
|:--|:--|:--|
| 向量模型 | Zhipu embedding-3, 1024 维，API 调用 | 7/10 |
| 存储方案 | pgvector + ChromaDB 降级，设计合理 | 8/10 |
| 索引策略 | ivfflat 索引，lists=100 | 7/10 |
| Embedding 缓存 | MemoryCache TTL=3600s，减少重复 API 调用 | 8/10 |

**优势**: pgvector + ChromaDB 双轨方案兼顾性能和容灾。Embedding 缓存命中高（用户常问相同问题），节省 API 费用。

**不足**:
- ivfflat 是近似索引，百万级数据建议升级为 HNSW
- Embedding 缓存仅基于 MD5，无语义相似查询去重能力
- 未评估本地 Embedding 模型（如 bge-m3）替代 API 的可能性——在离线或高并发场景下 API 调用是瓶颈

---

### 2.3 RRF 多路召回融合

| 维度 | 评价 | 评分 |
|:--|:--|:--|
| 算法正确性 | RRF 公式实现正确，k=60 为经验最优值 | 9/10 |
| 双路独立性 | 向量和 BM25 完全独立召回，互不干扰 | 9/10 |
| BM25 独有保留 | 48-52% 的 BM25 独有结果进入融合池（旧 hybrid=0%） | 9/10 |
| 降级机制 | BM25 不可用时自动降级为纯向量 | 8/10 |
| 短查询优化 | <15 字符自动 boost +10 候选，设计合理 | 8/10 |

**优势**: 这是整个系统最扎实的模块。从旧 hybrid（dense 优先去重，sparse 信号浪费）到独立双路 + RRF 融合，召回质量提升显著。BM25 直连 PG 全文索引，绕过 llama_index，性能好。

**不足**:
- BM25 使用 `to_tsquery('simple', ...)` 无词干提取和停用词，中文场景影响不大但英文会有问题
- 缺少对 RRF 融合权重的可配置化（当前 k=60 硬编码）
- 融合后无分数校准——RRF 分 (~0.03) 和向量分 (0~1) 不在同一量纲

---

### 2.4 Sentence Window Retrieval

| 维度 | 评价 | 评分 |
|:--|:--|:--|
| 设计合理性 | 子 chunk（精准检索）+ 父 chunk（完整上下文），业界标准方案 | 9/10 |
| 实现质量 | ChunkResult 数据结构清晰，ingestion 向后兼容普通模式 | 8/10 |
| 扩展效果 | 5.2x 上下文扩展（236→1215 字），实测数据支撑 | 9/10 |
| 自动检测 | chunk≥20 自动启用，无需人工干预 | 8/10 |
| 去重机制 | 多子→同一父去重，避免冗余 | 8/10 |

**优势**: 三体 20 万字全文实测验证，扩展比 5.2x 显著提升 LLM 上下文完整度。自动检测逻辑合理——短文档无需 SW，长文档自动启用。

**不足**:
- 父 chunk 存储在 PG 普通表，未做压缩或分页——超大文档（>1000 父 chunk）时单次查询可能返回过多数据
- 子/父比（3句:15句）硬编码在 chunker 中，不可配置
- `fixed_size` 和 `markdown_header` 策略不支持 SW——仅 sentence 和 recursive

---

### 2.5 两级检索（文档摘要索引）

| 维度 | 评价 | 评分 |
|:--|:--|:--|
| 设计理念 | Level 1 摘要→Level 2 chunk，业界标准方案 | 9/10 |
| Level 1 精度 | 80% Top-1 命中率（5 个三体查询中 4 个首选正确文档） | 8/10 |
| 过滤正确性 | 100%（所有 Level 2 结果 source 在 Level 1 目标内） | 9/10 |
| 降级路径 | 3 条降级路径覆盖全面（文档少、外部 doc_ids、PG 不可用） | 9/10 |
| 冷启动 | 新上传文档自动生成摘要+索引 | 8/10 |

**优势**: 降级路径设计是亮点——不是简单的"开/关"，而是根据文档数量、是否有外部 doc_ids、PG 是否可用三个维度自动决策。100% 过滤正确性说明 BM25 路也加了 source 过滤。

**不足**:
- Level 1 摘要搜索用余弦距离，与 chunk 搜索的 RRF 不在同一体系——两个阶段用不同算法，缺乏一致性
- 摘要向量和 chunk 向量用同一 Embedding 模型，但语义粒度不同（摘要 vs 片段），可能有偏差
- 跨领域查询时 Level 1 可能被误导（"倒计时"被员工手册干扰）

---

### 2.6 Reranker 精排

| 维度 | 评价 | 评分 |
|:--|:--|:--|
| 模型选择 | BGE-Reranker-v2-m3，MTEB 基准领先 | 9/10 |
| 子进程隔离 | 解决了 llama_index 与 FlagEmbedding 的 tokenizer 冲突 | 9/10 |
| 降级机制 | 子进程崩溃时降级为原始排序，自动重启 | 8/10 |
| 推理性能 | CPU 推理 ~7.6s/批，延迟较高 | 4/10 |
| 触发策略 | 仅深度搜索时触发（max_dense≤0.50），日常查询不经过 | 5/10 |

**优势**: 子进程隔离方案是本次开发中最有技术含量的创新——通过 `subprocess.Popen` + stdin/stdout JSON 协议，彻底解决了两个依赖库冲突导致 segfault 的问题。降级机制保证即使 Reranker 崩溃也不影响查询。

**不足**:
- **CPU 推理延迟过高**（~7.6s/批），导致仅能在深度搜索路径中使用
- **触发率低**：当前阈值 0.50 下，5 个三体查询全部跳过 Reranker。这意味着 Reranker 在大多数查询中形同虚设
- 无 GPU 加速支持
- 子进程首次启动需 ~5s（模型加载），无 warm-up 机制
- 未实现批量推理优化（逐对计算 query-doc，而非批量编码）

---

### 2.7 查询引擎（HyDE + 快/深路径决策）

| 维度 | 评价 | 评分 |
|:--|:--|:--|
| HyDE 实现 | LLM 生成假设答案→二次检索，标准实现 | 8/10 |
| 阈值决策 | max_dense ≤ threshold 触发深度搜索，逻辑清晰 | 7/10 |
| 阈值合理性 | 0.50 在 5 个三体查询中均不触发，阈值偏保守 | 5/10 |
| 缓存机制 | RAG 响应 TTL=300s + Embedding TTL=3600s | 8/10 |
| 并发控制 | 无并发限制，高并发下可能 LLM API 过载 | 4/10 |

**优势**: MembraneCache 双层缓存（响应 + Embedding）减少重复计算。HyDE 实现简洁，降级时静默返回 None。

**不足**:
- **阈值设置缺乏数据支撑**——0.50 是基于 5 个三体查询的推测，未在大规模查询上验证
- **"快路径"和"深度搜索"的边界模糊**——"雷志成怎么死的" max_dense=0.620 走快路径但回答质量差，max_dense 高 ≠ 回答质量好
- 缺少 A/B 测试框架来评估阈值选择
- 未对 LLM 调用做超时控制和重试

### 2.8 上下文管理

| 维度 | 评价 | 评分 |
|:--|:--|:--|
| Token 裁剪 | tiktoken cl100k_base，8000 token 预算 | 8/10 |
| 轮次裁剪 | 30 轮限制，防止上下文无限增长 | 7/10 |
| 摘要机制 | 200 条触发，保留 20 条，LLM 增量合并 | 8/10 |
| 摘要注入 | 拼接到 system prompt 的 [对话历史摘要] 段 | 7/10 |
| 多轮 RAG | RAG 查询不支持多轮对话上下文 | 3/10 |

**优势**: 摘要机制设计完整——增量合并而非全量重算，触发阈值和保留数量可配置。

**不足**:
- **RAG 查询和对话上下文是割裂的**——前端调用 `/query/stream` 时只传当前问题，不带历史对话。这意味着无法追问"那他后来怎么样了？"
- 摘要触发阈值 200 条偏高——大多数用户会话不会达到这个量
- 摘要注入位置在 system prompt 末尾，可能被长 system prompt 稀释

### 2.9 幻觉抑制

| 维度 | 评价 | 评分 |
|:--|:--|:--|
| Prompt 约束 | 逐句引用强制，含示例引导 | 8/10 |
| 置信度标记 | high/medium/low 三级，前后端贯通 | 7/10 |
| NLI 校验 | 未实现 | 0/10 |

**优势**: P0（Prompt 逐句引用）和 P1（置信度标记）都是零延迟方案，投入产出比高。

**不足**:
- Prompt 约束全靠 LLM 自觉——没有强制校验机制
- 置信度标记只基于 max_dense，未考虑 chunk 内容是否真正回答用户问题
- NLI 事实校验是行业中较成熟的方案但未引入

### 2.10 可观测性

| 维度 | 评价 | 评分 |
|:--|:--|:--|
| 日志覆盖率 | 9 个步骤全部有日志 | 9/10 |
| 日志分层 | DEBUG（中间步骤）+ INFO（结果），设计合理 | 8/10 |
| 文件持久化 | RotatingFileHandler，10MB×5 备份 | 8/10 |
| 耗时统计 | 总耗时，无分阶段耗时 | 5/10 |
| 监控告警 | 无 | 0/10 |

**优势**: 日志从 4 个关键点到 9 步全覆盖，是本次改进最大的进步。分级设计让日常运维不刷屏，排查时可切 DEBUG。

**不足**:
- 无分阶段耗时（向量搜索/BM25/SW/Reranker/LLM 各自耗时），无法定位性能瓶颈
- 无结构化日志（JSON 格式），不利于日志分析系统采集
- 无查询成功率/延迟的 metrics 统计

## 三、技术债务

| 优先级 | 问题 | 影响 |
|:--|:--|:--|
| P0 | Reranker 在日常查询中形同虚设（触发率 0%） | 最重量级的优化投入未产出 |
| P0 | RAG 不支持多轮对话 | 用户无法追问，体验割裂 |
| P1 | 阈值 0.50 缺乏数据支撑 | 快/深路径决策可能不准 |
| P1 | OCR 仅检测首页 | 扫描版 PDF 可能误走文本提取 |
| P1 | 无 LLM 调用超时/重试 | 网络抖动时查询可能卡死 |
| P2 | Reranker CPU 推理延迟高 | 即使触发也慢 |
| P2 | 无分阶段耗时统计 | 性能优化缺少数据依据 |
| P2 | 无并发控制 | 高并发 LLM API 可能超配额 |

## 四、优势总结

1. **架构完整度高**: 入库→切片→Embedding→多路召回→窗口展开→精排→两级检索→LLM 生成，主流 RAG 技术栈全覆盖
2. **RRF 融合扎实**: 独立双路 + RRF 融合 + BM25 独有保留，召回质量有实测数据支撑
3. **Sentence Window 效果好**: 5.2x 上下文扩展，196K 字长文档验证通过
4. **子进程隔离有创新性**: 解决了依赖库冲突导致 segfault 的工程难题，含降级保底
5. **可观测性提升显著**: 从 4 个日志点到 9 步全覆盖
6. **降级路径设计周全**: 两级检索 3 条降级、Reranker 崩溃降级、BM25 不可用降级

## 五、改进路线建议

```
近期 (1-2周):
  ├── P0: 让 Reranker 在日常查询中生效（降低阈值或改为始终运行）
  ├── P0: RAG 支持多轮对话（/query 接口传 session_id）
  └── P1: 阈值基于更大规模查询数据重新校准

中期 (2-4周):
  ├── P1: LLM 调用超时+重试
  ├── P1: 分阶段耗时统计
  └── P2: Reranker 性能优化（GPU/量化/缓存）

长期 (1-3月):
  ├── P2: NLI 事实校验
  ├── 本地 Embedding 模型评估
  └── 结构化日志 + 监控告警
```
