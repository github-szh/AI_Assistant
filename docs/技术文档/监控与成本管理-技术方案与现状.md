## 设计原则

1. **零外部依赖** — 不使用 Docker、Grafana、外部 Prometheus 服务器。所有指标采集、存储、展示都在 FastAPI 进程内完成。
2. **JSON 序列化安全** — 所有返回值不包含 `inf`/`NaN`，确保 Python 标准 `json.dumps` 直接可用。
3. **重启不丢数据** — 成本数据写入 SQLite（WAL 模式），进程重启后仍可查询历史累计。
4. **优雅降级** — GPU（pynvml 未安装时）、Redis（未连接时）、Phoenix（未运行时）各自独立降级，不影响核心功能。
5. **Prometheus 仅作临时采集** — Counter/Histogram/Gauge 在 `--reload` 时会被模块重新导入重置，因此关键数据（LLM 成本）同时写入 SQLite，HTTP 统计使用独立 in-memory dict。

## 模块详情

### 1. `metrics.py` — 指标定义 + 采集 + In-memory 缓冲

| 组件 | 说明 |
|------|------|
| Prometheus Counter | `llm_tokens_total`, `llm_cost_total`, `http_requests_total` — Prometheus 标准暴露 |
| Prometheus Histogram | `http_request_duration_seconds` — buckets: 0.01/0.05/0.1/0.25/0.5/1/2.5/5/10/30 |
| Prometheus Gauge | `system_cpu_percent`, `system_memory_*`, `system_disk_*`, `db_pool_*` |
| In-memory LLM buffer | `_llm_history` deque (maxlen=500) — 供 dashboard 快速读取最近调用 |
| In-memory HTTP dict | `_http_counts` — 避免 `--reload` 重置 Counter；dashboard 从此读取 |
| Pricing table | `_PRICES` dict: 8 chat + 2 embedding 模型，硬编码，单位: USD/1M tokens |
| `record_llm_call()` | 写 Prometheus Counter + 写 in-memory ring buffer + 写 SQLite |
| `get_latency_percentiles()` | 从 Prometheus Histogram bucket 计数计算 p50/p95/p99，过滤 +Inf 桶 |
| `collect_resources()` | 后台线程每 15s 调用，写 psutil 数据到 Prometheus Gauge |
| `collect_gpu()` / `collect_redis()` | 可选采集，失败时置空字典 |

### 2. `storage.py` — SQLite 持久化

| 表 | 字段 | 用途 |
|----|------|------|
| `llm_calls` | ts, provider, model, prompt_tokens, completion_tokens, cost, elapsed | 每次 LLM 调用记录，按 ID DESC 查询 |
| `http_requests` | ts, method, endpoint, status, duration | 预留（当前 HTTP 数据走 in-memory） |
| `rag_queries` | ts, query_hash, query_text, max_score, score_bucket, chunk_count, elapsed | RAG 检索质量追踪 |
| `alert_rules` | metric, operator, threshold, label, enabled | 告警规则（启动时 seed 4 条默认规则） |
| `alert_events` | ts, rule_id, label, metric, value, operator, threshold, acknowledged | 告警触发历史 |

函数: `init_db()`, `save_llm_call()`, `get_llm_calls()`, `get_cost_summary()`, `get_llm_call_count()`, `save_rag_query()`, `get_rag_query_stats()`, `init_alerts()`, `save_alert_event()`, `get_recent_alerts()`, `acknowledge_alert()`, `trim_old_calls()`

### 3. `dashboard.py` — JSON + HTML 端点

| 端点 | 返回 | 频率 |
|------|------|------|
| `GET /monitoring` | 完整 JSON: cpu, mem, disk, db_pool, gpu, redis, latency (p50/p95/p99), http, llm_tokens, llm_costs, llm_call_count, recent (LLM 调用), rag (质量), alerts | 前端每 5s 轮询 |
| `GET /dashboard` | HTML 页面 (Chart.js + 内联表格) | 直接浏览器访问 |
| `POST /api/alerts/ack` | `{"ok": true}` — 确认单条或全部告警 | 前端点击操作 |

### 4. `alerts.py` — 告警引擎

- 启动时 seed 4 条默认规则: CPU>90%, 内存>90%, 磁盘>90%, DB 连接池<20%
- 后台资源循环每 15s 调用 `evaluate_alerts()`
- 同规则 5 分钟内不重复触发（`_FIRED` dict 限频）
- 触发事件写入 `alert_events` 表，同时在日志输出 WARNING

### 5. 前端 `MonitoringView.vue`

| 标签页 | 内容 |
|--------|------|
| 概览 | 6 统计卡片 (CPU/内存/磁盘/DB/LLM调用/LLM成本) + 延迟百分位 + GPU + Redis |
| 质量 | RAG 检索质量: 平均分 + 总查询 + 分数分布柱状图 + 饼图 |
| 性能 | HTTP 请求按端点 + LLM Tokens 按模型 + LLM 成本 + 磁盘使用 |
| 明细 | 最近 LLM 调用表 (时间/Provider/模型/Tokens/耗时/成本) + CSV 导出 |
| 告警 | 告警历史表 + 全部确认按钮 |

所有标签页共享 5s 自动刷新，使用 `api.get('/monitoring')` 获取 JSON。

### 6. 与 Arize Phoenix 的关系

| 方面 | 监控系统 | Phoenix |
|------|----------|---------|
| 用途 | 成本 + 资源 + 质量 + 告警 | LLM trace 可视化 (span 级) |
| 存储 | SQLite (data/monitoring.db) | 无持久化 (全内存，重启即清) |
| 数据 | 结构化数值 (Token数/耗时/分数) | 非结构化 trace (prompt/response/span tree) |
| 依赖 | 零依赖 (全部内置于 FastAPI) | 可选安装 (`arize-phoenix`) |
| 默认 | 始终启用 | 需要手动 `start_phoenix.py` |
| 连接 | 不依赖外部服务 | 监听 `localhost:6006` |

两者是互补关系：监控系统负责"谁花了多少钱、系统健康吗"，Phoenix 负责"LLM 为什么这么回答、trace 链路是怎样的"。

### Phoenix 启用流程

1. 设置 `PHOENIX_ENABLED=true`（默认 false）
2. 安装依赖: `pip install arize-phoenix openinference-instrumentation-openai`
3. 重新启动应用（`start.bat` 或手动启动后端的 `uvicorn`）

启用后：
- 后端在 lifespan 中自动调用 `setup_tracing()`，通过 OTLP HTTP 向 localhost:6006 推送 trace
- OpenAI SDK 自动埋点（覆盖 Ali/DeepSeek/OpenAI 三个 provider）；Zhipu 通过手动 OTel span 包装
- 监控看板出现 🔄 追踪标签页，内嵌 Phoenix UI（通过后端 proxy 避免跨域问题）
- `start.bat` 自动启动 Phoenix 进程

### 禁用时的行为

`PHOENIX_ENABLED=false`（默认）:
- `setup_tracing()` **不会被调用**，OTel SDK 不初始化
- Phoenix 相关端点返回 503/未运行状态
- 前端追踪标签页显示"Phoenix 已禁用"提示
- Phoenix 进程不被启动
- 监控系统的所有其他功能（成本、延迟、资源、RAG 质量、告警）完全不受影响

### 安全防护

Phoenix 集成在任何故障场景下**不影响应用正常启动**：

| 场景 | 影响 |
|------|------|
| `arize-phoenix` 未安装 | `scripts/start_phoenix.py` 打印错误并退出；`setup_tracing()` 中的 `OpenAIInstrumentor` import 失败被 `except Exception` 捕获，不阻塞启动 |
| Phoenix 进程启动失败 | `start` 命令独立窗口运行，失败不影响后端窗口 |
| Phoenix 与后端同时启动（竞争条件） | `setup_tracing()` 中 OTLP exporter 在 Phoenix 未就绪时静默丢弃 trace，应用正常响应 |
| Phoenix 运行中崩溃 | OTLP exporter 内部重试后放弃，应用正常运行 |
| `httpx` 代理超时 | `/phoenix/{path}` 端点 catch Exception 返回 502，前端 iframe 正常显示错误页 |
