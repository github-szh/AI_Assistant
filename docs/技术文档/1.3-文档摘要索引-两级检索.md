# 文档摘要索引（两级检索）— 实施计划

## Context

大库场景（100+ 文档）下，全库向量检索会导致噪声淹没信号。比如查询"病假"时，技术文档中的"健康检查"语义相近但完全不相关，占用了宝贵的 top-k 位置。

两级检索解法：
- Level 1：搜文档摘要 → 确定 top-3 相关文档
- Level 2：搜这 3 篇文档的 chunks → 候选集从 8000 收窄到 120

好消息：上传时已在生成 AI 摘要存入 `t_document.summary`，只需 embed + 索引即可利用。

此项同时补上 P0 遗留问题：**doc_ids 过滤链路**（5 层断链一次补齐）。

## 核心流程

```
查询
  │
  ├── Level 1: query embed → 搜 doc_summaries 向量表 → top-3 doc_ids
  │
  ├── Level 2: query embed + MetadataFilters(doc_id IN [...]) → 搜 data_documents
  │     └── RRF 融合 (vector + BM25)
  │
  ├── Sentence Window 展开 (子 → 父)
  │
  ├── Reranker 精排
  │
  └── LLM 生成
```

当外部传入 doc_ids（未来前端文档选择器）时，跳过 Level 1 直接用传入的 IDs。
当文档数 < 10 时，跳过 Level 1（全库检索更高效）。

**新增 `_insert_summary(doc_id, summary, embedding, filename, chunk_count)`**：

**新增 `_search_summaries(query_embedding: list[float], top_k: int) -> list[dict]`**：
```sql
SELECT doc_id, summary, filename, chunk_count,
       1 - (embedding <=> %s::vector) AS similarity
FROM doc_summaries
ORDER BY embedding <=> %s::vector
LIMIT %s
```

### 5. `src/knowledge/query_engine.py` — 两级检索编排

**`_retrieve()` 新增 `doc_ids` 参数**：

```python
def _retrieve(self, question: str, top_k: int, doc_ids: list[str] | None = None):
```

核心逻辑：

```
if doc_ids is not None:
    target_ids = doc_ids           # 外部指定，跳过 Level 1
else:
    doc_count = _count_documents()
    if doc_count < settings.two_stage_min_docs:
        target_ids = None          # 文档太少，全库检索
    else:
        # Level 1: 搜摘要
        query_emb = embed_mgr.encode_query(question)
        relevant = _search_summaries(query_emb, settings.summary_search_top_k)
        target_ids = [r["doc_id"] for r in relevant] if relevant else None

# Level 2: 带过滤检索
nodes = _do_retrieve(question, doc_ids=target_ids)
```

**`_cache_key()` 加入 doc_ids**：

```python
@staticmethod
def _cache_key(question: str, top_k: int, doc_ids: list[str] | None = None) -> str:
    base = f"rag:{hashlib.md5(question.encode()).hexdigest()}:{top_k}"
    if doc_ids:
        base += ":" + ",".join(sorted(doc_ids))
    return base
```

**新增 `_count_documents()`**：

```python
def _count_documents() -> int:
    """Count distinct documents in the vector store."""
    try:
        conn = psycopg.connect(settings.pg_dsn, connect_timeout=3)
        count = conn.execute("SELECT COUNT(*) FROM t_document").fetchone()[0]
        conn.close()
        return count
    except Exception:
        return 0
```

## 效果验证

### 验证 1：Level 1 — 摘要搜索

```
查询: "请假需要什么证明？"
命中: 2 篇文档
  [1] sim=0.495  test_hr.txt
      摘要: "该员工手册主要规定了公司各类假期的天数、申请条件及违规后果..."
  [2] sim=0.485  test_hr.txt
      摘要: "该员工手册主要规定了公司的假期制度、加班管理及纪律处分..."
```

查询先在 `doc_summaries` 摘要向量表里搜索。这个表存的是每篇文档的 AI 摘要（不是原文 chunk），只有几十条记录。

结果说明：
- 命中了 2 条摘要（同一个文件被上传了两次，产生了两个版本）
- 相似度 0.485-0.495，说明摘要内容和查询语义相关
- 这两条的 doc_id 作为 Level 2 的过滤目标

如果没有两级检索：查询会直接搜全部 121 个 chunk（包含请假制度、钻井液论文、Claude Code 教程、简历等），噪声占比很高。有了两级检索：这一步把候选范围从"121 个 chunk / 7 篇文档"收窄到"相关文档的 chunk"。

### 验证 2：Level 2 — 全库 vs 过滤检索

**全库检索（不用两级检索）**：

```
全库检索: 3 chunks
  [1] test_sw.txt — "病假需提供医院开具的病假条。病假工资按最低工资标准80%发放..."
  [2] test_sw.txt — "丧假为1-3天。根据亲属关系远近确定具体天数。"
  [3] test_sw.txt — "公司规定员工享有带薪年假。年假天数根据工龄计算..."
```

3 条结果全部来自 test_sw.txt（之前测试 Sentence Window 时上传的请假制度文档）。

**两级检索（先用摘要定位文档，再在文档内搜）**：

```
两级检索 (过滤到 2 篇文档):
结果: 1 chunk
  [1] test_hr.txt — "员工手册：年假5-15天，病假需医院证明，婚假3天，产假按国家规定..."
```

1 条结果来自 test_hr.txt（HR 员工手册文档）。

**两路对比解读**：

| | 结果来源 | 原因 |
|:--|:--|:--|
| 全库检索 | test_sw.txt（请假制度文档）| 这个文档 chunk 多、语义匹配好，在全局排名中占优 |
| 两级检索 | test_hr.txt（员工手册）| 摘要搜索判断员工手册和"请假条件"最相关，限制了搜索范围 |

不同场景下各自的优势：
- 全库检索在小库（< 10 篇）时没问题，反倒更全面
- 两级检索在大库（100+ 篇）时优势明显——先排除 95% 不相关的文档，再在 5% 相关文档中精搜

### 验证 3：过滤正确性

```
所有结果 source 在目标内: ✓
```

验证过滤链路的正确性——Level 2 返回的每个 chunk，其 `source` 字段必须属于 Level 1 选出的文档 ID 列表。

本次过滤目标：`["1d33de69a546", "db6eab66b554"]`
实际返回的 source：`"1d33de69a546"` → 在目标列表中 ✓

**发现并修复的 Bug**：BM25 搜索路没有加 doc_ids 过滤，导致 RRF 融合时混入了未过滤的 BM25 结果。修复后双路（向量 + BM25）都受 doc_ids 约束。

### 验证 4：降级路径

```
KB 文档数: 7
触发阈值: 10
Level 1 状态: 跳过 (文档不足)
```

两级检索有一个启动条件——知识库至少要有 `two_stage_min_docs`（默认 10）篇文档，Level 1 才启用。理由：
- 7 篇文档时，全库 chunk 也就 ~120 个，向量搜索直接扫完全没问题
- 100 篇文档时，全库 chunk 可能上万个，必须先缩小范围

另外两种降级场景：

| 场景 | 行为 |
|:--|:--|
| KB < 10 篇 | 跳过 Level 1，全库检索 |
| 外部传入了 doc_ids（前端文档选择器）| 跳过 Level 1，直接用传入的 ID 过滤 |
| doc_summaries 表为空（PG 挂了）| 跳过 Level 1，降级全库检索 |

### 整体数据流

```
用户问: "请假需要什么证明？"
        │
        ▼
┌─ Level 1 ──────────────────────┐
│  doc_summaries 表搜索           │
│  结果: test_hr.txt × 2         │
│  doc_ids: [1d33de69a546, ...]  │
└──────────────┬─────────────────┘
               │
               ▼
┌─ Level 2: data_documents 搜索 ─┐
│  VectorSearch + filters        │  ← 只搜目标文档的 chunks
│  BM25Search  + source filter   │  ← 双路都加过滤约束
│         │                       │
│         ▼                       │
│  RRF 融合 → 展开 → 精排        │
│  结果: 1 chunk (test_hr.txt)   │
└────────────────────────────────┘
               │
               ▼
          LLM 生成答案
```
