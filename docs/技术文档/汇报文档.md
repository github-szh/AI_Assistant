## 2. 上下文管理

### 2.1 功能概述

AI Assistant 实现了完整的多轮对话上下文管理，包含三个子系统：

```
每条新消息
  │
  ├── [1] Token 裁剪 — tiktoken cl100k_base 编码, 8000 token 预算
  │       文件: src/utils/trim_messages.py
  │
  ├── [2] 轮次裁剪 — 最多保留 30 轮对话
  │       文件: src/utils/trim_messages.py
  │
  ├── [3] 摘要注入 — 将历史摘要拼接到 system prompt
  │       文件: src/api/routes/chat.py:42-45
  │
  └── [4] 摘要更新 — 当未摘要消息超过 200 条时触发
          文件: src/utils/summarizer.py
```

### 2.2 Session 摘要机制

**触发条件**（src/config.py:88-89）：

```python
chat_summarize_trigger: int = 200    # 未摘要用户消息超过200条时触发
chat_summarize_keep_recent: int = 20  # 保留最近20条不摘要
```

**工作流程**（src/utils/summarizer.py:33-107）：

```
1. 统计 t_session_message 中 summarized=false 的用户消息数
2. 如果 > 200 → 取最旧的 (count - 20) 条
3. 与现有的 rolling summary (t_session_info.summary) 合并
4. 调用 LLM 生成新的 300 字中文摘要
5. 更新 t_session_info.summary，标记这些消息 summarized=true
6. LLM 调用失败时 → 降级为 truncate + "[早期对话]" 标记
```

**摘要注入**（src/api/routes/chat.py:42-45）：

```python
if req.session_id:
    summary = get_summary(req.session_id)  # 从 DB 获取
    if summary and messages and messages[0].get("role") == "system":
        messages[0]["content"] += "\n\n[对话历史摘要]\n" + summary
```

**Token 预算**（src/config.py:83-84）：


## 3. 切片策略

### 3.1 四种策略对比

| 策略 | 原理 | 适用场景 | 断句依据 |
|:--|:--|:--|:--|
| `fixed_size` | 按固定字符数切分 | 通用文本 | 固定1024字符 |
| `sentence` | 按句子边界切分 | 叙事文本、长文档 | 句号/问号/感叹号/换行 |
| `markdown_header` | 按 Markdown 标题层级切分 | 技术文档、API文档 | `#`/`##`/`###` 标题 |
| `recursive` | 递归降级：段落→句子→滑动窗口 | 混合格式文档 | 段落优先级最高，遇超长文本自动降级到句子，再不行到字符级 |

### 3.2 策略详解

#### fixed_size（固定大小切片）

最基础的策略。按 `chunk_size=1024` 字符切分，`chunk_overlap=100` 字符的重叠区防止关键信息被截断。

```
原文: "第一章...（5000字）"
→ chunk_1: [0:1024]
→ chunk_2: [924:1948]  ← 100字符重叠
→ chunk_3: [1848:2872]
...
```

#### sentence（句子级切片）

以句号、问号、感叹号和换行为边界切分，保持语义完整性。

```
原文: "汪淼是一名物理学家。他发现了异常现象。这让他非常不安。"
→ chunk_1: "汪淼是一名物理学家。他发现了异常现象。"
→ chunk_2: "这让他非常不安。"
```

#### recursive（递归降级切片）

最智能的策略，三段降级保证不丢数据：

```
1. 尝试按段落拆分（\n\n）
   └→ 如某段超过 chunk_size → 降级
2. 对超长段落按句子拆分（。！？）
   └→ 如某句仍超过 chunk_size → 降级
3. 对超长句子按字符滑动窗口切分
```

### 3.3 配置方式

```python
# src/config.py:72-74
chunk_strategy: str = "sentence"  # 默认策略
chunk_size: int = 1024
chunk_overlap: int = 100
```

上传时可通过 Query 参数覆盖：

```bash
curl -X POST "/upload?strategy=recursive" -F "file=@doc.pdf"
curl -X POST "/upload?strategy=sentence"  -F "file=@doc.pdf"
curl -X POST "/upload?strategy=fixed_size" -F "file=@doc.pdf"
curl -X POST "/upload?strategy=markdown_header" -F "file=@doc.md"
```

### 3.4 状态标注

✅ 四种切片策略已全部实现。

## 4. 查询方案

### 4.1 方案全景

项目实现了 5 种查询/召回路径，按复杂度递增：

```
方案1: 纯向量搜索
  简单、快速 → 模式: mode="default", 只用 embedding 相似度

方案2: 纯 BM25 搜索
  精确关键词匹配 → PostgreSQL to_tsquery, ts_rank 排序

方案3: RRF 多路召回融合（当前默认）
  方案1 + 方案2 → RRF 加权融合

方案4: RRF + HyDE 重写
  方案3 + LLM 生成假设答案 → 用假设答案文本二次检索

方案5: RRF + HyDE + Reranker 精排（深度搜索）
  方案4 + BGE-Reranker-v2-m3 Cross-encoder 精排
```

### 4.2 RRF（Reciprocal Rank Fusion）多路召回融合

**核心原理**（src/knowledge/retrieval.py:82-125）：

向量搜索和 BM25 搜索是两套独立的排序体系。旧方案把两者直接合并（dense 优先去重），BM25 精确命中关键词的信号被浪费。

RRF 公式：

```
score(node) = Σ 1/(k + rank_i)

其中 k=60（经验最优值），rank_i 是 node 在第 i 路搜索中的排名（0-based）
```

**举例说明**：

查询"汪淼"，一个 chunk 在向量搜索排第 5、BM25 排第 1：

```
RRF 分数 = 1/(60+5+1) + 1/(60+1+1)
         = 1/66 + 1/62
         = 0.0152 + 0.0161
         = 0.0313（两路加权）
```

如果只在向量中出现（BM25 没有）：

```
RRF 分数 = 1/(60+rank) （只有一路贡献，分数明显更低）
```

**三路重叠分析**（以"汪淼"查询为例）：

```
向量 top-30:    30 条
BM25  top-30:   30 条  ← 两路独立召回
两路重合:        3 条  ← RRF 双重加权 → 排在最前面
仅向量命中:     27 条  ← 保留（旧方案也会保留）
仅 BM25 命中:   27 条  ← 保留（旧方案会丢弃！这是RRF的关键价值）
```

**代码位置**（src/knowledge/retrieval.py）：

- `_bm25_search()`: 第 33 行 — 独立 BM25 搜索，直连 PG 全文索引
- `_rrf_fusion()`: 第 82 行 — RRF 融合算法
- `_coarse_retrieve()`: 第 212 行 — 统一粗召回入口，串联向量+BM25+RRF

### 4.3 HyDE（Hypothetical Document Embeddings）重写查询

**原理**（src/knowledge/query_engine.py:208-221）：

当向量相似度偏低时，说明原始查询和文档的语义距离较远。HyDE 让 LLM 先生成一个"假设答案"，用这个答案文本做二次检索——假设答案的语义更接近真实文档。

```
原始查询: "物理学家为什么自杀"
    ↓ max_dense 偏低 (≤0.65)
HyDE 生成: "物理学家们因为发现了物理学规律在时间和空间上不均匀，
           实验每次结果都不同，基础物理定律被动摇，因此选择了结束生命..."
    ↓ 用这段文本二次检索
用 HyDE 文本做 embedding → 向量搜索 → 更容易匹配到相关文档
```

### 4.4 两级检索（文档摘要索引）

**原理**（src/knowledge/query_engine.py:53-90）：

大知识库场景（15+ 篇文档）下，全库检索会引入大量无关文档的噪声。两级检索先搜文档摘要定位相关文档，再在这些文档内搜 chunk。

```
查询: "汪淼发现了什么异常?"
  │
  ├── Level 1: query embedding → 搜 doc_summaries 表 → top-3 文档
  │     [1] 三体测试.txt (0.623)
  │     [2] 长文档测试.pdf (0.428)
  │     [3] reg_fixed_size.txt (0.426)
  │
  └── Level 2: 在 top-3 文档的 chunk 中搜索
        VectorSearch + MetadataFilters(source IN [doc_ids])
        + BM25Search + source filter
        → RRF 融合 → 仅来自这 3 篇文档的 chunk
```

**降级条件**（不会滥用两级检索）：

| 场景 | 行为 |
|:--|:--|
| KB < 10 篇文档 | 跳过 Level 1，全库检索（小库没必要两级） |
| 外部传入 doc_ids | 跳过 Level 1，直接用传入的 ID 过滤 |
| doc_summaries 表为空 | 跳过 Level 1，降级全库检索 |

### 4.5 快路径 vs 深度搜索的阈值决策

关键配置（src/config.py:61-65）：

```python
retrieval_coarse_k: int = 40        # RRF 粗召回候选数
```

**决策逻辑**（src/knowledge/query_engine.py:96-110）：

```python
top_score = getattr(nodes[0], "_dense_max_score", None)  # 向量最大相似度

    nodes = _do_retrieve(hyde_text, deep=True, ...)         # 二次检索+Reranker
else:
    # 快路径: RRF + SW 直接返回（~3秒）
```

**实际查询示例**：

## 5. Reranker 功能和原理

### 5.1 什么时候用到 Reranker

Reranker 在查询方案的**深度搜索路径**中触发（见 4.5 节的决策逻辑）：

```
Stage 1 向量相似度 ≤ 0.65
  → HyDE LLM生成假设答案
    → 用假设答案做二次检索 (RRF融合)
      → Sentence Window 展开
        → **Reranker Cross-encoder 精排** ← 这里
          → top-5 给 LLM
```

Reranker 是"最后一道关"——在粗召回筛选出候选后，用更精准的模型重新排序，确保 LLM 收到的是最相关的 5 条。

### 5.2 BGE-Reranker-v2-m3 原理

**Bi-encoder（向量搜索） vs Cross-encoder（Reranker）：**

```
Bi-encoder（向量搜索）:
  query → [Encoder] → embedding (1024维向量)
  doc   → [Encoder] → embedding (1024维向量)
  score = cosine_similarity(query_emb, doc_emb)
  
  优点: 快，可预先计算文档向量
  缺点: query和doc独立编码，无交互，精度受限

Cross-encoder（Reranker）:
  query + doc → [Joint Encoder] → relevance score
  
  优点: 联合编码，精度更高
  缺点: 慢，每对(query,doc)都要重新算
```

**BGE-Reranker-v2-m3** 是 BAAI 开源的 Cross-encoder 模型：

- 模型大小：2.2 GB
- 架构：XLMRoberta 基座 + 交叉注意力层
- 输入：`[CLS] query [SEP] document [SEP]`
- 输出：一个 0~1 之间的相关性分数（原始 logit → min-max 归一化后）
- 比 Bi-encoder 精度提升约 10-20%（在 MTEB 基准上）

### 5.3 子进程隔离方案（关键创新）

**问题**：`llama_index` 和 `FlagEmbedding`（BGE-Reranker 的依赖库）共用 HuggingFace tokenizers 底层，两个库在同一进程中同时导入后，Reranker 做推理时 segfault（内存访问错误）。

**根因**：两个库各自初始化 HuggingFace tokenizers 的不同后端，冲突导致已加载的 BGE 模型内部状态损坏。

**解决方案**：子进程隔离架构

```
主进程 (FastAPI/uvicorn)              子进程 (reranker_worker.py)
  ┌─────────────────────┐              ┌──────────────────────┐
  │ llama_index           │              │ FlagEmbedding  ONLY   │
  │ pgvector              │   stdin      │ XLMRobertaTokenizer   │
  │ src.knowledge.*       │ ═══════════→ │ BGE-Reranker-v2-m3    │
  │                       │   JSON       │ (2.2GB, FP16)         │
  │ Reranker.rerank()     │ ←═══════════ │                        │
  │   ↓                   │   stdout     │ model.compute_score()  │
  │ subprocess.Popen      │   JSON       │                        │
  └─────────────────────┘              └──────────────────────┘
```

## 6. 长文档 Embedding

### 6.1 核心挑战

普通 chunk（1024 字符固定切分）在长文档上面临两个问题：

1. **信息碎片化**：检索命中孤立的 1024 字符片段，LLM 看不到上下文
2. **检索精度下降**：20 万字的文档有 3,824 个 chunk，0.8% 的覆盖率

### 6.2 Sentence Window Retrieval 方案

**设计理念**：用小粒度做索引（精准检索），用大窗口做上下文（完整喂 LLM）。

```
父 chunk（~15 句，给 LLM 看）→ 存入 chunk_contexts 表
子 chunk（~3 句，做向量索引）→ 存入 data_documents 向量表
子 chunk.metadata.parent_id → 检索后查到父 chunk → 展开
```
