## 修复明细

### Bug 1：Super admin 无法下载文档

**文件：** `src/api/routes/documents.py`（`download_document` 函数）

**问题：** `WHERE doc_id = %s AND tenant_id = %s` 无 super_admin 旁路，tenant_id=NULL 导致 SQL 永远不匹配，返回 404。

**修改：** 加 `is_super` 判断，与同文件的 `_query_pg_documents` 和 `delete_document.py` 对齐。

```python
# 改前
tenant_id = user.get("tenant_id")
row = conn.execute(
    "SELECT filename, file_type FROM t_document WHERE doc_id = %s AND tenant_id = %s",
    [doc_id, tenant_id],
).fetchone()

# 改后
is_super = user.get("role") == "super_admin"
tenant_id = user.get("tenant_id")
if is_super:
    row = conn.execute(
        "SELECT filename, file_type FROM t_document WHERE doc_id = %s", [doc_id],
    ).fetchone()
else:
    row = conn.execute(
        "SELECT filename, file_type FROM t_document WHERE doc_id = %s AND tenant_id = %s",
        [doc_id, tenant_id],
    ).fetchone()
```

### Bug 2：Super admin 无法操作自己的会话

**文件：** `src/api/routes/sessions.py`（`get_session`、`rename_session`、`delete_session` 三条路由）

**问题：** 三条路由的 SQL 都有 `AND tenant_id = %s` 但没有 `is_super` 旁路。唯独 `list_sessions` 做了旁路，不一致。

**修改：** 三条路由各加 `is_super` 判断——super_admin 不加 tenant_id 过滤，非 super_admin 保留过滤。

涉及函数：
- `get_session`（GET /{sid}）：查询 `SELECT ... WHERE id=%s`（is_super） vs `WHERE id=%s AND tenant_id=%s`
- `rename_session`（PATCH /{sid}）：`WHERE id=%s AND user_id=%s` vs `WHERE id=%s AND user_id=%s AND tenant_id=%s`
- `delete_session`（DELETE /{sid}）：`WHERE id=%s AND user_id=%s` vs `WHERE id=%s AND user_id=%s AND tenant_id=%s`

### Bug 3：聊天接口无租户校验

**文件：** `src/api/routes/chat.py`（`POST /chat`）

**问题：** 写入 `t_session_message` 时不验证 session 的租户归属。跨租户用户知道 session_id 就能写入消息。

**修改：** 写消息前加 session 归属校验：

```python
# 新增
if req.session_id and req.messages:
    is_super = user.get("role") == "super_admin"
    tenant_id = user.get("tenant_id")
    async with get_pg_connection() as conn:
        if is_super:
            row = conn.execute(
                "SELECT 1 FROM t_session_info WHERE id=%s", [req.session_id]
            ).fetchone()
        else:
            row = conn.execute(
                "SELECT 1 FROM t_session_info WHERE id=%s AND tenant_id=%s",
                [req.session_id, tenant_id],
            ).fetchone()
        if not row:
            raise HTTPException(403, "无权访问该会话")
```

同时补充了 `HTTPException` 的导入（原文件缺少）。

### 问题 4：Super admin 上传文档 tenant_id=NULL

**问题：** admin 的 `t_user.tenant_id = NULL`，上传文档时 `t_document.tenant_id = NULL`，导致其他用户无法查看和搜索这些文档。若 admin 被降级，文档变孤儿。

**解决方案：** 采用方案 2——将 admin 的 tenant_id 设置为默认租户（id=1），跨租户能力靠 `role == "super_admin"` 判断。

**数据库修改：**
```sql
UPDATE t_user SET tenant_id = 1 WHERE username = 'admin' AND tenant_id IS NULL;
UPDATE t_document SET tenant_id = 1 WHERE tenant_id IS NULL;
UPDATE t_session_info SET tenant_id = 1 WHERE tenant_id IS NULL;
UPDATE data_documents SET metadata_ = jsonb_set(metadata_::jsonb, '{tenant_id}', '"1"'::jsonb)::json
    WHERE COALESCE(metadata_->>'tenant_id', '') IN ('', 'None') OR metadata_->>'tenant_id' IS NULL;
```

修复结果：
- t_user：1 行（admin）
- t_document：4 行
- data_documents：504 行

### 问题 5：二级检索对 super_admin 永远跳过

**文件：** `src/knowledge/query_engine.py`（`_count_documents`）、`src/knowledge/index_store.py`（`_search_summaries`）

**问题：** 两个函数的 SQL 无条件 `WHERE tenant_id = %s`，tenant_id=NULL 时永远返回空。导致 super_admin 的 RAG 查询跳过二级检索优化（Level 1 文档摘要预筛选），每次全库搜索。

**修改：** 与其他检索函数对齐，tenant_id 为 None 时不设租户过滤：

`_count_documents`:
```python
# 改前
rows = conn.execute("SELECT COUNT(*) FROM t_document WHERE tenant_id = %s", [tenant_id])

# 改后
if tenant_id is not None:
    rows = conn.execute("SELECT COUNT(*) FROM t_document WHERE tenant_id = %s", [tenant_id])
else:
    rows = conn.execute("SELECT COUNT(*) FROM t_document")
```

`_search_summaries`:
```python
# 改前：WHERE tenant_id = %s 无条件

# 改后：分 if tenant_id is not None / else 两条 SQL，else 不加 WHERE
```

## Windows reload 后无法重启

> 日期：2026-06-07

### 根因

uvicorn `--reload` 在 Windows 上终止旧 worker 进程后，`RotatingFileHandler` 持有的日志文件句柄未释放。新进程启动时 `setup_logging()` 再打开同一文件失败，进程直接崩溃。

### 修复

**文件：** `src/observability/logging_config.py`

- 保存 `_file_handler` 模块级引用
- 新增 `shutdown_logging()` 函数：从 root/uvicorn logger 移除 handler 并调用 `close()` 释放 Windows 文件句柄

**文件：** `src/api/main.py`

- lifespan shutdown 中 `close_pool()` 之后调用 `shutdown_logging()`

### 附带优化

**文件：** `src/api/deps.py`

- `_Pool.close()`：每个连接先 `rollback()` + `autocommit=True` 再 `close()`，避免事务状态阻塞关闭
- `close_pool()`：`asyncio.wait_for(timeout=5)` 包裹，防止卡死 shutdown

## SW 展开丢弃无 parent_id 的 chunk

> 日期：2026-06-07

### 根因

`sentence_window` 模式（大文档自动启用）给 chunk 加了 `parent_id`，小文档没有。检索时两类 chunk 混在一起，`_expand_to_parents()` 收集到 `parent_id` 后进入"展开模式"，在第二轮循环中：`if not pid or pid in emitted: continue` — 没有 `parent_id` 的 chunk 被直接跳过。

### 修复

**文件：** `src/knowledge/retrieval.py`（`_expand_to_parents` 第 167-174 行）

三个分支独立处理：

- `not pid` → `result.append(node)` 原样保留
- `pid in emitted` → 去重跳过
- 正常展开 → 用 parent 内容替换；若 parent 查不到 → 回退保留原始 child
