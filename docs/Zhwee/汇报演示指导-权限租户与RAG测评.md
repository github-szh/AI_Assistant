### 2.2 功能介绍与流程

#### 角色体系（4 级权限模型）

```
super_admin (超级管理员)
  │  ★ 通配符权限 "*"，绕过所有权限检查
  │  ★ 跨租户访问，查看所有租户数据
  │  ★ 创建/管理租户，创建任意角色用户
  │
tenant_admin (租户管理员)
  │  12 项权限：租户查看、用户管理、文档CRUD、聊天、监控、质量、系统设置
  │  只能管理本租户的资源和用户
  │  不能创建 super_admin 或 tenant_admin
  │
editor (编辑者)
  │  8 项权限：文档CRUD、聊天CRUD、知识查询、质量查看
  │  不能管理用户和租户
  │
viewer (阅览者)
     4 项权限：聊天收发、知识查询、质量查看
     纯浏览，不能上传/删除文档
```

#### 权限检查流程

```
用户请求 → JWT 解码 → 提取 {user_id, username, role, tenant_id}
                         │
                         ▼
              require_permission("document:upload")
                         │
                     role == "super_admin" ?  ──是──► 放行
                         │否
                         ▼
              检查 ROLE_PERMISSIONS[role] 是否包含该权限
                         │
                    包含？ ──是──► 放行
                         │否
                         ▼
                    返回 HTTP 403 Forbidden
```

#### 租户数据隔离流程

```
用户上传文档
  │  文档写入 t_document（附带 tenant_id）
  │  向量 chunk 写入 data_documents（metadata 中保存 tenant_id）
  ▼
用户提问 (RAG)
  │
  ├─ Level 1: 文档摘要搜索 → WHERE tenant_id = %s
  ├─ Level 2: Vector 搜索 → metadata_->>'tenant_id' = %s
  ├─ Level 2: BM25 搜索 → metadata_->>'tenant_id' = %s
  └─ 文档列表/下载 → WHERE tenant_id = %s

例外：role == "super_admin" → 跳过所有 tenant_id 过滤，全库搜索
```

### 2.3 实现原理

#### Q1：为什么不每次请求都查数据库验证权限？

**答：** 采用 JWT 无状态认证。用户登录时将 `{user_id, username, role, tenant_id}` 签入 JWT，每个请求从 token 中解码即可获得完整身份，无需查库。优点：性能高、不依赖数据库可用性。代价：角色变更需要用户重新登录获取新 token。

#### Q2：如何防止 tenant_admin 越权操作其他租户的数据？

**答：** 两层防护：
1. **SQL 层** — 所有数据查询都带 `WHERE tenant_id = %s`，从 SQL 语句层面杜绝跨租户数据泄露
2. **向量检索层** — pgvector 的 metadata 过滤 `metadata_->>'tenant_id' = %s`，即使 chunk 召回阶段也不混入其他租户数据

#### Q3：如果 super_admin 的 tenant_id 是 NULL，SQL 的 `WHERE tenant_id = %s` 会怎样？

**答：** 这正是之前修复的 Bug。代码中所有数据访问点都用 `if is_super:` 分支（不加 tenant_id 过滤）和 `else:` 分支（加过滤），共修复了 14 个数据访问点，覆盖文档、会话、检索、上传、删除、下载、聊天等全部接口。

#### Q4：角色层级保护是如何实现的？

**答：** 服务端维护 `role_hierarchy = {"viewer": 0, "editor": 1, "tenant_admin": 2, "super_admin": 3}`。修改角色时检查：
- 操作者不能修改角色级别 ≥ 自己的用户
- 操作者不能将用户提升到 ≥ 自己的角色级别
- 只有 super_admin 能操作 super_admin

1. **演示顺序建议：** 先演示角色差异（用例1，视觉直观）→ 再演示租户隔离（用例2，核心价值）→ 最后演示防护机制（用例3、4，体现安全设计），由浅入深。

#### 完整评测流程

```
用户输入问题 + 标准答案(选填)
         │
         ▼
① 检索管线（~22s）
  ├─ Level 1: 文档摘要预筛选 — Embedding 搜索相似文档
  ├─ Level 2: 混合召回 — Vector + BM25 → RRF 融合
  ├─ 阈值判断 — 最高分 > 0.65 走快路径，否则触发深度搜索
  └─ HyDE + Reranker（条件触发）— 假设答案辅助检索 + 交叉编码器精排
         │
② LLM 生成（~3s）
  └─ 加载 Prompt 模板 + 检索上下文 → deepseek-v4-pro 生成回答
         │
③ 五维度质检（并行 ~10s）
  ├─ 检索质量 — 纯数值统计（零延迟）
  ├─ 安全性   — LLM Judge 语义评判
  ├─ 事实性   — LLM 分解 claims + jieba 支撑检查
  ├─ 答案正确性 — F1 + 语义相似度（需标准答案）
  └─ 相关性   — Embedding + jieba（零 token 成本）
         │
④ 干预决策
  └─ 按优先级匹配规则 → block / degrade / warn / none
         │
⑤ 响应返回
  └─ { answer, sources, quality{5维度}, intervention }
```

### 3.3 实现原理

#### Q1：五个维度分别怎么评测的？各自的原理是什么？

**答：**

| 维度 | 原理 | LLM 调用 |
|------|------|----------|
| **检索质量** | 从检索结果的 similarity score 计算平均值、最高分、通过率、离散度，纯数学统计 | 0 次 |
| **安全性** | 调用 Judge LLM（deepseek-v4-flash）进行语义评判，检查是否有有害/敏感内容 | 1 次 |
| **事实性** | LLM 将回答分解为原子 claims → jieba 检查每个 claim 是否在检索上下文中有支撑 → 计算支撑率 | 1 次（分解） |
| **答案正确性** | LLM 分别分解 answer 和 ground_truth 为 claims → 计算 F1 + 语义相似度 + 数值一致性 → 加权融合 | 2 次（分解 ×2） |
| **相关性** | Embedding 余弦相似度（50%）+ jieba 关键词覆盖率（30%）+ 长度因子（20%） | 0 次 |

合计单次测评：3-4 次 LLM 调用（使用轻量 flash 模型控制成本）。

#### Q2：为什么要用独立的 Judge 模型而不是和生成用同一个模型？

**答：** 这是**交叉评判**原则——让裁判和选手不同队。如果生成回答的模型同时评判自己的回答，会存在"自我增强偏差"（认为自己说的都对）。用不同的模型（deepseek-v4-pro 生成 + deepseek-v4-flash 评判）可以降低这种偏差。另外 flash 模型更快更便宜，适合做评判这种不需要深度推理的任务。

#### Q3：HyDE 是什么？为什么能提高检索质量？

**答：** HyDE = Hypothetical Document Embeddings（假设文档嵌入）。当用户问题与知识库文档存在"词汇鸿沟"（用户用口语提问，文档用专业术语）时，直接用问题向量搜效果不好。HyDE 的做法是：
1. 先让 LLM 生成一段"假设答案"（不需要准确）
2. 用假设答案的向量去搜索
3. 因为假设答案的词汇分布更像专业文档，召回率更高

相当于"用一个假的答案去钓真的文档"。

#### Q4：事实性检查为什么用 jieba 分词而不是 Embedding？

**答：** 设计上两者结合：
- **jieba**：做精准的 claim 级别匹配（"这句话有没有依据？"），即使一个词不同也能检测
- **Embedding**：做兜底的语义相似度（"整体意思对吗？"），当 claim 分解失败时降级使用

两者互补，jieba 提供可解释性（能说出"4/5 条事实有依据"），Embedding 提供鲁棒性。

#### Q5：如果用户没有输入标准答案，answer_correctness 怎么处理？

**答：** 返回 `passed=true, score=0.5`，details 说明"无标准答案，跳过"。不影响其他维度的评测，也不触发任何干预动作。

### 3.4 我的建议

1. **演示顺序建议：** 先演示用例 1（基础测评，无 ground_truth）建立认知 → 再用例 2（带 ground_truth 展示"标准答案对比"的震撼感）→ 最后用例 3（展示系统诚实反馈低质检索）。

2. **可能被问到的问题（提前准备）：**
   - "评测分数准吗？" → 如实说明：LLM Judge 不是完美的，存在误判可能（如之前 safety 误判法律文本），但对产品迭代和问题定位非常有价值
   - "为什么不实时测？" → 成本考量：每次 Chat 多 3-4 次 LLM 调用，延迟 +10s。所以 Chat 流程已移除质检，RAG测评作为**按需诊断工具**保留
   - "能测多快？" → 检索 ~22s（HyDE+Reranker 占大头）+ 生成 ~3s + 质检 ~10s（并行），总计 ~35s

3. **可以补充的价值点：**
   - 评测不是给用户看的（用户只关心答案对不对），而是给**开发/运维人员**用的——验证知识库质量、排查检索问题、对比策略效果
   - 五个维度覆盖了 RAG 全链路：检索→生成→内容安全→事实准确→相关匹配

4. **后续可优化方向：**
   - 批量评测：支持上传测试集（JSON），批量跑完生成评测报告
   - 历史对比：保存每次评测结果，对比不同配置（chunk_size、检索策略）的效果
   - 评测基线：对标准测试集建立 baseline，每次改动后自动跑对比

#### 成本计算公式

```python
# src/monitoring/metrics.py
_PRICES = {
    "deepseek-v4-pro":   (2.00, 8.00),   # 输入 $2/M-token, 输出 $8/M-token
    "deepseek-v4-flash": (0.30, 1.20),   # v4-flash 便宜 6 倍
    "qwen-plus":         (0.80, 2.00),
    "gpt-4o":           (2.50, 10.00),
    ...
}

成本 = (prompt_tokens × 输入价格 + completion_tokens × 输出价格) / 1,000,000
```

Token 数从 LLM API 响应的 `usage` 字段中获取实际值，非估算。

### 4.3 实现原理（Q&A）

#### Q1：成本是怎么算出来的？数字准吗？

**答：** 定价表硬编码了主流模型的价格（$/百万 token），每次 LLM 调用后从 API 响应的 `usage` 字段取**实际 token 消耗**，乘以对应模型单价。准确性取决于 API 返回的 token 数（DeepSeek/OpenAI 的 usage 字段是准确的）。

#### Q2：为什么用 SQLite 而不是 PostgreSQL？

**答：** 监控数据是时序日志型（append-only），不需要复杂查询。SQLite 的优势：
1. 零运维 — 单文件 `monitoring.db`，备份就是复制文件
2. WAL 模式 — 并发读写不冲突
3. 不依赖 pgvector — 即使 PostgreSQL 宕机，监控仍可独立运行
4. 隔离性 — 监控数据不污染业务数据库

#### Q3：数据会保留多久？会撑爆磁盘吗？

**答：** 默认保留策略：
- 内存缓冲：最近 500 条 LLM 调用（约 2MB）
- SQLite：无自动清理（`trim_old_calls()` 函数存在但未调度），目前数据量在 KB 级，短期无风险。后续可加定时清理任务（如每天删 90 天前数据）。

#### Q4：和 Prometheus + Grafana 是什么关系？

**答：** 项目暴露了 `/metrics` 端点（Prometheus 标准格式），可以接入外部 Prometheus 抓取。但仪表盘**不依赖 Prometheus 服务器**——所有数据同时写入内存和 SQLite，自给自足。设计理念：单机部署不需要额外运维 Prometheus，但支持按需接入。

#### Q5：不同租户的监控数据会混在一起吗？

**答：** RAG 质量数据（`rag_queries` 表）记录了 `tenant_id`，可按租户隔离。LLM 调用成本是全局的（所有租户共享 LLM API），不做租户拆分。
