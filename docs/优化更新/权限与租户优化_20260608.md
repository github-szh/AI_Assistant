## 建议（按优先级）

### 第一优先：修复数据泄露漏洞（C1、C5、M1）

**C1** `_get_chunks()` 是文档详情页获取片段内容的底层查询，原先完全不按 `tenant_id` 过滤，只要两个租户的文档产生相同 `doc_id`（12 位 hex UUID），A 租户即可读取 B 租户的文档片段。**C5** `_query_pg_documents()` 的 LEFT JOIN 缺少 tenant 过滤条件，vector_chunks 计数可能混入其他租户的数据。**M1** `_fetch_parent_contexts()` 在 tenant_id 为 None 时回退为全库搜索。

#### ✅ 已实施（2026-06-08）

**C1 — `_get_chunks()` 增加 `tenant_id` 过滤**

`_get_chunks()` 接收可选的 `tenant_id` 参数，SQL 动态追加 `AND metadata_->>'tenant_id' = %s`。参数保持 `Optional[int]` 签名兼容，但 None 时安全降级为空结果而非全库查询；`metadata_->>'tenant_id'` 是 JSONB 字符串，传参用 `str(tenant_id)` 保持类型一致。

`src/api/routes/documents.py`
```python
def _get_chunks(doc_id: str, tenant_id: int | None = None) -> list[str]:
    conn = None
    try:
        conn = get_pg_connection()
        sql = "SELECT text FROM data_documents WHERE COALESCE(metadata_->>'source', metadata_->>'doc_id')=%s"
        params = [doc_id]
        if tenant_id is not None:
            sql += " AND metadata_->>'tenant_id' = %s"
            params.append(str(tenant_id))
        rows = conn.execute(sql, params).fetchall()
        return [r[0][:500] for r in rows]
    except Exception as exc:
        logger.warning("获取文档片段失败: %s → %s", doc_id, exc)
        return []
    finally:
        if conn:
            conn.close()
```

**C5 — LEFT JOIN 增加租户过滤**

`_query_pg_documents()` 的 LEFT JOIN ON 子句增加 `AND dd.metadata_->>'tenant_id' = %s`。tenant 过滤加在 ON 子句而非 WHERE，避免将 LEFT JOIN 降级为 INNER JOIN。

`src/api/routes/documents.py`
```python
rows = conn.execute("""
    SELECT
        td.doc_id, td.filename, td.file_type, td.parser_used,
        td.chunks_count, td.file_size, td.uploaded_at, td.pages,
        td.summary,
        count(dd.id) as vector_chunks
    FROM t_document td
    LEFT JOIN data_documents dd
        ON COALESCE(dd.metadata_->>'source', dd.metadata_->>'doc_id') = td.doc_id
        AND dd.metadata_->>'tenant_id' = %s
    WHERE td.tenant_id = %s
    GROUP BY td.doc_id, td.filename, td.file_type, td.parser_used,
             td.chunks_count, td.file_size, td.uploaded_at, td.pages, td.summary
    ORDER BY td.uploaded_at DESC
""", [str(tenant_id) if tenant_id else None, tenant_id]).fetchall()
```

**M1 — `_fetch_parent_contexts()` 安全降级**

`_fetch_parent_contexts()` 在 `tenant_id is None` 时直接返回空字典并记录警告，不再执行全库查询，防止匿名或缺失租户时跨租户泄露。

`src/knowledge/index_store.py`
```python
def _fetch_parent_contexts(parent_ids: list[str], tenant_id: int | None = None) -> dict[str, dict]:
    if not parent_ids:
        return {}
    if tenant_id is None:
        logger.warning("tenant_id is None, skipping parent fetch to prevent cross-tenant leak")
        return {}
    ...
    rows = conn.execute(
        "SELECT parent_id, doc_id, content, filename, chunk_index "
        "FROM chunk_contexts WHERE parent_id = ANY(%s) AND tenant_id = %s",
        [parent_ids, tenant_id],
    ).fetchall()
    ...
```

### 第二优先：JWT 实时验证与权限缓存刷新（C3、C4）

**C3** JWT 解码后直接信任 payload 中的 role 和 tenant_id，不校验用户当前是否被禁用、角色是否变更、租户是否被禁用。**C4** 权限缓存从进程启动起永不过期。

#### ✅ 已实施（2026-06-08）

**C3 — JWT 实时校验**

新增 `_verify_user()` 查询 DB 确认用户活跃、角色、租户状态，结果通过 `MemoryCache` 缓存 30 秒。`get_current_user()` 解码 JWT 后调用该函数校验，缓存未命中或校验失败返回 401。用户状态变更最多滞后 30s 生效，安全优先 —— 缓存未命中时回退为拒绝请求。

`src/api/routes/auth.py`
```python
def _verify_user(user_id: int) -> dict | None:
    """查询数据库确认用户/租户状态，结果缓存 30 秒。"""
    from src.storage.cache import get_memory_cache
    cache = get_memory_cache()
    cache_key = f"user_verify:{user_id}"
    cached = cache.get(cache_key)
    if cached is not None:
        return cached

    conn = _get_pg()
    try:
        row = conn.execute(
            """SELECT u.username, r.name AS role, u.tenant_id, t.is_active AS tenant_active
               FROM t_user u
               JOIN t_role r ON u.role_id = r.id
               LEFT JOIN t_tenant t ON u.tenant_id = t.id
               WHERE u.id = %s AND u.is_active = TRUE""",
            [user_id],
        ).fetchone()
        if not row:
            return None
        if row[3] is not None and not row[3]:
            return None
        result = {"username": row[0], "role": row[1], "tenant_id": row[2]}
        cache.set(cache_key, result, ttl=30)
        return result
    except Exception as exc:
        logger.warning("用户状态校验失败: %s", exc)
        return None
    finally:
        conn.close()


def get_current_user(authorization: str | None = Header(None)) -> dict:
    """Dependency: extract user from JWT Bearer token, verify against DB."""
    if not authorization or not authorization.startswith("Bearer "):
        raise HTTPException(401, "未提供有效的认证令牌")
    try:
        payload = decode_jwt(authorization[7:])
        user_id = payload["user_id"]

        info = _verify_user(user_id)
        if info is None:
            raise HTTPException(401, "用户不存在或已被禁用")
        return {
            "user_id": user_id,
            "username": info["username"],
            "role": info["role"],
            "tenant_id": info["tenant_id"],
        }
    except jwt.ExpiredSignatureError:
        raise HTTPException(401, "认证已过期，请重新登录")
    except HTTPException:
        raise
    except Exception:
        raise HTTPException(401, "认证无效")
```

**C4 — 权限缓存 TTL + 双重检查锁**

新增 `_ROLE_PERMISSIONS_LOADED_AT` 时间戳（60 秒 TTL）和 `threading.Lock` 双重检查锁。并发请求下仅首次加载查库，后续直接返回缓存，角色-权限变更最多滞后 60s 生效。

`src/api/permissions.py`
```python
import threading
import time

_ROLE_PERMISSIONS_CACHE: dict[str, list[str]] | None = None
_ROLE_PERMISSIONS_LOADED_AT: float = 0
_CACHE_TTL = 60
_CACHE_LOCK = threading.Lock()


def _get_permissions() -> dict[str, list[str]]:
    global _ROLE_PERMISSIONS_CACHE, _ROLE_PERMISSIONS_LOADED_AT
    now = time.time()
    if _ROLE_PERMISSIONS_CACHE is None or (now - _ROLE_PERMISSIONS_LOADED_AT) > _CACHE_TTL:
        with _CACHE_LOCK:
            # 双重检查锁定：获锁后再次检查，避免重复加载
            if _ROLE_PERMISSIONS_CACHE is None or (now - _ROLE_PERMISSIONS_LOADED_AT) > _CACHE_TTL:
                _ROLE_PERMISSIONS_CACHE = _load_role_permissions()
                _ROLE_PERMISSIONS_LOADED_AT = now
    return _ROLE_PERMISSIONS_CACHE
```

### 第三优先：注册接口加固（M3）

**M3** 注册接口无任何防护：密码最短仅 4 位、无速率限制、任何人都可自动创建个人租户。

#### ✅ 已实施（2026-06-08）

**M3 — 注册接口加固**

注册接口新增三项防护：`RateLimiter(max_requests=3, window_seconds=60)` 每 IP 每 60 秒最多 3 次注册（Redis 不可用时 fail-open 放行）；密码最小长度 4→8；新增 `invite_only_registration` 配置项，启用后不允许自动创建个人租户。

`src/api/routes/auth.py`
```python
@router.post("/register", response_model=AuthResponse)
async def register(req: RegisterRequest, request: Request):
    # 限流：每 IP 每 60 秒最多 3 次注册
    from src.storage.cache import RateLimiter
    limiter = RateLimiter(max_requests=3, window_seconds=60)
    client_ip = request.client.host if request.client else "unknown"
    if not limiter.is_allowed(f"register:{client_ip}"):
        logger.warning("注册限流触发: IP=%s, username=%s", client_ip, req.username)
        raise HTTPException(429, "注册过于频繁，请稍后再试")

    if len(req.username) < 2 or len(req.password) < 8:
        raise HTTPException(400, "用户名至少2位，密码至少8位")

    # 邀请制模式：不允许自动创建个人租户
    if settings.invite_only_registration and not req.tenant_code:
        raise HTTPException(400, "当前为邀请制注册，请提供租户编码")
    ...
```

## 优化后的效果验证说明

### P0 数据泄露漏洞修复 验证（C1、C5、M1）

| 编号 | 缺陷 | 验证方式 | 预期结果 |
|------|------|----------|----------|
| **C1** | `_get_chunks()` 跨租户泄露 | A 租户上传 doc_X，B 租户请求 `/documents/doc_X` 的详情 | B 租户看到 404 或 chunks 为空数组，不会看到 A 租户的文档片段 |
| **M1** | `_fetch_parent_contexts()` 全库搜索 | 在未传入 `tenant_id` 的场景（如匿名 token）触发 Sentence Window 检索 | 函数返回空字典，不会返回全租户的 parent chunks |
| **C5** | LEFT JOIN 跨租户计数 | A 和 B 租户各有 doc_X，在 B 租户的文档列表查看 doc_X 的 `vector_chunks` | 只统计 B 租户自身的 vector chunks，不包含 A 租户的 |

### P1 认证与权限加固 验证（C3、C4、M3）

| 编号 | 缺陷 | 验证方式 | 预期结果 |
|------|------|----------|----------|
| **C3** | JWT 角色不可撤销 | 将用户角色从 `editor` 改为 `viewer`，用旧的 JWT token 请求上传文档 | 请求被拒绝（403 或 401），不会因旧 JWT 中的 `editor` 角色而放行 |
| **C3** | JWT 租户不可撤销 | 禁用用户所属租户，用已有的 JWT token 请求任意接口 | 返回 401 "用户不存在或已被禁用" |
| **C4** | 权限缓存不刷新 | 在 DB 中修改 `t_role_permission`，等待 60 秒后检查权限判断 | 60 秒内用旧缓存，60 秒后自动使用新配置，无需重启服务 |
| **M3** | 注册无限制 | 同一 IP 在 60 秒内连续 4 次注册 | 第 4 次返回 429 "注册过于频繁" |
| **M3** | 密码过短 | 用 4 位密码注册 | 返回 400 "密码至少8位" |
| **M3** | 邀请制模式 | 设置 `invite_only_registration=True` 后不带 `tenant_code` 注册 | 返回 400 "当前为邀请制注册，请提供租户编码" |

## 下一步实施的缺陷优化

### 🔴 CRITICAL（可直接导致跨租户数据泄露或权限绕过）

#### C2. `data_documents` 表的 `tenant_id` 仅存在于 JSONB `metadata_` 中

`src/knowledge/ingestion.py:44-51` 将 `tenant_id` 作为 `"tenant_id": str(tenant_id)` 写入 `metadata_` JSONB 字段，`data_documents` 表本身**没有 `tenant_id` 列**。这意味着：

- 无 `FOREIGN KEY` 引用 `t_tenant`，数据库层无法保证租户引用的完整性
- 无 `NOT NULL` 约束，`tenant_id` 可空 = chunk 可能泄漏到所有租户
- 所有查询通过 `metadata_->>'tenant_id' = %s` 做字符串比较，与 `t_document.tenant_id` 的整数类型不一致，存在类型隐式转换风险
- 无数据库索引（报告 🟡5），全表扫描过滤

---

### 🟠 MAJOR（重要缺陷，可能导致隔离失效或管理失控）

#### M2. 文件系统无租户隔离

`src/api/routes/upload.py:96-98` 所有租户的上传文件存储在 `{data_dir}/documents/{doc_id}{ext}` 同一目录，无租户子目录。虽然数据库有 `tenant_id` 过滤，但文件系统层面完全无法隔离。结合全局异常处理器向客户端泄漏 `str(exc)`（报告 C5），文件路径可能被意外暴露，其他租户可直接通过路径访问文件。

#### M4. 多处直连数据库绕过连接池

`auth.py:43-49`、`sessions.py:17-23`、`query_engine.py:469`、`index_store.py` 中多处定义了独立的 `_pg()` 直连函数，不使用 `deps.py` 中的 `ConnectionPool`。认证路径作为每个请求必经之路，在高并发下不断创建/销毁 TCP 连接。报告 🟠M3 已指出约 60% 的数据库操作不使用连接池。

---

### 🟡 MODERATE（设计不合理但不易直接触发安全漏洞）

#### 11. 角色名硬编码散落在多处

`"viewer"`、`"editor"`、`"tenant_admin"`、`"super_admin"` 作为裸字符串散落在 `auth.py:109`（`WHERE name = 'viewer'`）、`permissions.py:68,77`（`default="viewer"`、`role == "super_admin"`）、`admin.py:29,162,167,181,214`（角色验证逻辑）等 8+ 处。如果数据库中的角色名被修改，部分功能会静默出错。

#### 12. `can_manage_tenant()` 与 `require_permission()` 职责重叠且校验模式不统一

`permissions.py:74-79` 的 `can_manage_tenant()` 逻辑本质上是用户维度的补充校验。`update_tenant` 路由同时使用了 `require_permission("tenant:manage")` 和 `can_manage_tenant()`，而 `list_tenants` 路由却手写 `if user.get("role") != "super_admin"` 而非调用同一函数。租户管理和用户管理的多个路由各自用不同的方式做跨租户校验，维护负担大、出错风险高。

#### 13. `tenant_id` 在核心数据路径中大量为 `Optional` — 静默 None = 无隔离

`query_engine.py`、`index_store.py`、`retrieval.py` 等 10+ 处函数签名中 `tenant_id: int | None = None`。上游从 JWT `.get("tenant_id")` 获取，如果 JWT 解析异常或编码时未携带该字段，`tenant_id` 静默为 None 并向下传递。`_search_summaries`、`_count_documents`、`_bm25_search`、`_coarse_retrieve` 等函数仍允许 None——尽管它们 SQL 中用 `WHERE tenant_id = %s`，None 传参导致 SQL WHERE 永假返回空结果，行为不可预期且难以调试。

#### 14. Session 路由的 `get_session` 使用双层校验与同文件其他方法不一致

`src/api/routes/sessions.py:80-82` 在 SQL 中以 `WHERE id=%s AND tenant_id=%s` 校验后，又在应用层额外校验 `row[2] != user["user_id"]`。而同文件的 `rename_session`、`delete_session` 仅依靠 SQL WHERE 中的 `user_id` 和 `tenant_id` 做校验。两种模式混用：前者在应用层 403 拒绝（暴露用户存在信息），后者在 SQL 层 404 返回（未找到=信息不敏感）。行为不一致增加维护成本和安全隐患。

#### 15. 无操作审计日志

整个项目没有任何审计日志。租户创建/禁用、用户角色变更、文档删除等敏感操作只留下普通应用日志（甚至残留 `print()`，报告 🟡4）。无法追溯"谁在何时做了什么"——在等保合规或安全事件溯源场景下是硬伤。

---

### 最致命的根本缺陷（尚未修复）

**多租户隔离完全依赖应用层手动编写 WHERE `tenant_id = %s`**，没有任何数据库层（PostgreSQL Row-Level Security）或框架层（中间件自动注入）的兜底机制。

目前每处数据访问都需要开发者手动添加 `AND tenant_id = %s`，一旦某处代码遗漏了这个过滤条件，就是跨租户数据泄露——`_get_chunks()` 已经是已修复的真实遗漏实例。在 15+ 个独立 SQL 查询中维持这一约束，人力成本高且不可靠。
